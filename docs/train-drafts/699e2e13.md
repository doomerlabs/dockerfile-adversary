## What we want to improve

Detect when a Dockerfile references a build-time version token such as $BUILD_VERSION or ${BUILD_VERSION} but fails to declare or re-declare the corresponding ARG in the consuming stage, leaving the token unset at build time. Examples include a Node.js Dockerfile that uses LABEL version="${APP_VERSION}" without ARG APP_VERSION and a multi-stage Go Dockerfile that injects -X main.version=${BUILD_VERSION} without ARG BUILD_VERSION in the final stage.

## Why this matters

When a consuming stage lacks ARG for a referenced build-time token, Docker leaves the token unset and builds can silently fall back to workspace or CI defaults, producing mismatched tags or embedded metadata. Calling out the missing ARG prevents unexpected image tags or binaries that lack intended release metadata.

## Examples

- Node.js example: a Dockerfile with LABEL version="${APP_VERSION}" that omits ARG APP_VERSION, causing labels and tags to fall back to package.json or CI defaults.
- Go example: a multi-stage Dockerfile that runs go build -ldflags "-X main.version=${BUILD_VERSION}" in the final stage while ARG BUILD_VERSION is only declared in the builder stage, so the injected symbol is unset in the final binary.

## Keep it focused

- A Dockerfile intentionally reads a workspace-managed version at build time (for example from package.json or Cargo.toml) and does not reference any build-time ARG token, so omitting ARG should not be flagged.
- A Dockerfile already declares ARG BUILD_VERSION in the exact stage where LABEL, ENV, or ldflags consume it, so no finding should be emitted because the token is available to that stage as declared.
